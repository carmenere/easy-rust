# Философия ЯП
**Философия ЯП** - **набор фундаментальных идей**, лежащих в основе дизайна языка.<br>
*Философия ЯП* **формирует мышление разработчика**.<br>

<br>

Например, ключевой момент философии **ZCA** (*Zero Cost Abstraction*) - высокоуровневые конструкции бесплатны во время исполнения.<br>

<br>

# Рантйам языка программирования
Рантйам языка программирования - это код "вокруг" программы.<br>

<br>

Типичные компоненты рантайма ЯП:
- сборщик мусора;
- JIT комплиятор;
- интерпретатор;
- представление объектов в памяти;

<br>

Рантайм во многих ЯП берет на себя именно **управление памятью**, т.к. автоматическое управление памятью очень слиьно экономит время программиста.<br>

<br>

**Цена рантайма** - чем больше делает райнтайм ЯП, тем меньше надо делать вам.<br>

Чем "жирнее" рантайм, т.е. чем больше функций берет на себя, тем:
- меньше скорость
- больше размер бинарника
- сложнее переиспользование - сложно библиотеку из одного ЯП переиспользовать в другом с другим рантаймом
- больше потребление RAM

<br>

## Оператор `as`
В Rust **нет** неявного привидения типов. Для **явного привидения** типов используется оператор `as`:
```rust
fn main() {
    let x = 1_u16;
    let y: u32 = x as u32; // ✅ - Ok
}
```

<br>

Приведение **более широкого** типа к **более узкому** (например, **из** `u32`, `i32`, `usize` **в** `u8`) через оператор `as` выполняется как **truncation** (усечение). Эта операция является **безопасной** (**safe**) в терминах Rust — она никогда **не** **вызывает** панику (**panic**) или неопределенное поведение (**UB**), **но может привести к потере данных**:
```rust
let a: u32 = 15;      // В памяти (32 бита): 00000000 00000000 00000000 00001111
let b: u8 = a as u8;  // Взяли последние 8 бит: 00001111
// Результат b = 15
```

<br>

А вот через метод `into()` уже **нельзя** преобразовать **более широкий** тип к **более узкому**, т.к. `.into()` выполняет преобразование **без потерь**:
```rust
fn main() {
    let x = 1_u32;
    let y: u16 = x.into(); // ❌ - ERROR
    let y: u16 = x as u16; // ✅ - Ok
}
```

А реобразовать **узкий** тип к **более широкому** через `.into()` **можно**:
```rust
fn main() {
    let x = 1_u16;
    let y: u32 = x.into(); // ✅ - Ok
    let y: u32 = x as u32; // ✅ - Ok
}
```

<br>

Любой `char` можно привести к `u8`, но такое приведение корректно сработает только для кодировок **ASCII** и **Latin-1**, т.е. для символов в диапазоне `\x00`–`\xFF`:
```rust
let a = 'ъ';
let b: u8 = a as u8;
```

## Арифметика с переполнением
```rust
fn main() {
    let x = i32::MAX;
    // let y = x + 1; // ❌ - Compile time error
    let y = add(x, 1); // - in debug mode - panic, in --release mode - it prints -2147483648
    println!("{}", y);
}
```

<br>

```rust
fn main() {
    let x = i32::MAX;

    let y = x.wrapping_add(2);
    assert_eq!(y, i32::MIN+1);

    let y = x.saturating_add(5);
    assert_eq!(y, i32::MAX);

    let (y, o) = x.overflowing_add(1);
    assert!(o);
    assert_eq!(y, i32::MIN);

    let y = x.checked_add(1);
    match y {
        Some(y) => {println!("No overflow, result: {}", y)},
        None => println!("Overflow!")
    }
}
```

<br>

Методы для арифметики с переполнением:
- `x.wrapping_add(N)` - при переполнении *результат* будет `i32::MIN + (N-1)`;
- `x.saturating_add(N)` - при переполнении *результат* **всегда** будет `i32::MAX`;
- `x.overflowing_add(N)` - если было переполнение, то *результат* `y` как у `wrapping_add`, дополнительно флаг `o` устанавливается в `true`;
- `x.checked_add(N)` - если было переполнение, то *результата нет* - `None`, если не было то *результат*: `Some(y)`;

# Ссылки и указатели
**Ссылки** (`&T` и `&mut T`), позволяют **использовать** объект **без владения**.<br>

<br>

**Инварианты ссылок**:
- *ссылка* **НЕ может быть** `NULL`;
- *сслыка* **гарантирует**, что **объект жив**;

<br>

**Указатели** (`*const T` и `*mut T`).<br>

<br>

**Инварианты указателей**:
- *указатель* **может быть** `NULL`;
- *указатель* **НЕ гарантирует**, что **объект жив**;

<br>

Поэтому, разыменование указателя - **unsafe**.<br>
В основном используются для **ffi** и **оптимизаций**.<br>

<br>

**Ссылки vs. Указатели**:
- **ссылка** указывает на объект, который точно есть;
- **указатель** указывает куда-то в память, но никаких гарантий не дает;

<br>

## Box<T>
`Box<T>`:
- указывает на данные **в куче** и **дает все гарантии ссылок**;
- **освобождает данные** при выходе из скоупа;

<br>

# Стек и куча
Свойства **стека**:
- **локален для потока**;
- автоматически освобождается;
- размер известен во время компиляции;
- время жизни привязано к функции;
- адресное пространство выделяется при старте потока - по умолчанию в Linux 8Mb, но маппинг в физическую память ленивый;

<br>

Свойства **кучи**:
- **глобальна для процесса**;
- медленнее: стоимость лукапа в дереве;
- явные malloc/free;
- любой размер;
- произвольное время жизни;

<br>

Работа с кучей ведется через **специальную структуру**, которая хранит в себе свободные блоки. Как правило это *RB tree* или *AVL tree*.<br>
Когда мы просим аллокатор выделить память под данные, аллокатор идет в эту структуру данных и ищет в ней свободный блок нужного размера.<br>
Т.о. выделение памяти в куче это еще и стоимость лукапа в дереве.<br>
В **многопоточной программе** - **аллокатор общий на все потоки**, а значит еще и **синхронизация нужна**: локи или атомарные операции.<br>

<br>

**Проблемы кучи**:
- на каждый malloc звать free нужно ровно 1 раз;
  - позвать free 0 или больше 1 раза - это ошибка;

<br>

**Проблемы стека**:
- стек может переполняться, переполнение стека это UB;

<br>

В Rust используется подход **guard page**, когда после памяти под стек вставляется **специальная страница памяти**, обращение к которой вызывает **исключение**.<br>

<br>

# Блоки
**Блок** `{}` - это **выражение** (**expression**). **После блока не ставится** `;`.<br>

Если в блоке больше одного выражения, то в конце каждого выражения, **кроме последнего**, должна ставится `;`.<br>
**Точка с запятой** `;` превращает *выражение* в *инструкцию* (**statement**).<br>

Можно сказать, что *блок* состоит из **инструкций** (**statement**) и одного **последнего** (**хвостового**) **выражения**.<br>

**Значение блока** - значение *хвостового выражения* в блоке.<br>
После *хвостового выражения* в блоке `;` **не** ставится.<br>

<br>

**Пример 1**:
```rust
fn main() {
    struct S1 {v: i32}
    struct S2(i32);
    struct S3;
}
```

После `S1` **нет** `;`, т.к. после блока не ставится `;`.<br>
А вот после `S2` и `S3` **нужна** `;`, т.к. уже нет блока.<br>

<br>

**Пример 2**:
```rust
fn main() {
    let b1: i32 = {1 };
    let b2: () = {1; /* результат хвостового выражения unit */};
}
```

- у `b1` тип `i32`
- у `b2` тип `()`, т.к. все что до `;` - отсекается и возвращается только все, что следует после последней `;`

<br>

# if
`if ...` - тоже **выражение** (**expression**):
```rust
fn main() {
    let r1: i32 = if true {
        4
    }
    else {
        5
    }; // т.к. let

    if true {
        4;
    }
    else if 4 > 0 {
        5;
    } else {
        6;
    }
}
```

<br>

**Точка с запятой** `;` после `if` **нужна только** в `let r = if ... ;`.<br>
Если блок `if <cond> {}` последний в некотором скоупе - то `;` **не** требуется.<br>

Если нет блока `else` - то результат всего выражения `()`, т.е. в таком случае `if {}` должна возвращать `()`:
```rust
    let r = if 5 > 0 {
        9 // ❌ - ERROR, ожидается (), т.к. нет else {} части
    }; // т.к. let
```

<br>

Если блок `while <cond> {}` последний в некотором скоупе - то `;` **не** требуется.<br>

```rust

        9 // ❌ - ERROR, ожидается ()
    }; // т.к. let
```

# loop
Специальный тип бесконечного цикла - `loop {}`, данный цикл возвращает тип `!` - **never type**.
*Never type* `!` может приводиться к любому другому типу:
```rust
fn main() {
    let x: ! = loop {  };
    let x: u32 = loop {  };
}
```

<br>

Циклы `loop` и `while` отличаются информацией про поток управления:

- `while`
```rust
fn main() {
    let v;
    while true {
        if true {
            v = 92;
            break;
        }
    };
    println!("{}", v); // ❌ - ERROR:
}
```

- `loop`
```rust
fn main() {
    let v;
    loop {
        if true {
            v = 92;
            break;
        }
    };
    println!("{}", v); // ✅ - Ok
}
```

В первом случае **ошибка**, т.к. с точки зрения компилятора, `while <cond> {}` может завершаться по условию, а значит мы моежм выйти из него не только через `break`, а через условие `<cond>`. Поэтмоу с точки зрения компилятора, переменная `v` может быть неициализированной в момент обращения к ней.<br>

Во втором случае все **ок**, т.к. из `loop` мы можем выйти **только** через `break` и он один в ветке где инициализируется `v`. А значит, если мы вышли из `loop`, переменная `v` гарантированно инициализирвоанна.

<br>

Если мы добавим блок `else { break; }` - то во втором варианте тоже **появится ошибка**.<br>
Если мы добавим блок `else { loop {} }` - то во втором варианте ошибки **не** будет, т.к. мы из `else` никогда не выйдем:
```rust
fn main() {
    let v;
    loop {
        if true {
            v = 92;
            break;
        } else {
            loop {}
        }
    };
    println!("{}", v);
}
```

# Lifetimes
`'a` - это **lifetime parameter**, который содержит **время жизни ссылки** (lifetime ссылки), но **конкретное время жизни**, которое подставляется в `'a`, **определяется компилятором** при вызове функции.<br>
Напрямую влиять на значения *lifetime parameters* (`'a`, `'b`) программист не может, но программист может определять взаимосвязи между *lifetime parameters*.<br>

```rust
struct S {
    v: i32,
}

fn main() {
    let r: &i32;
    {
        let s: S = S{v: 10};
        let rs: &S = &s;
        r = f(rs);
    }
    println!("{}", *r);

    fn f<'a>(x: &'a S) -> &'a i32 {
        &x.v
    }
}
```

<br>

**Сигнатура** `fn f<'a>(x: &'a S) -> &'a i32` требует, чтобы **lifetime** **ссылок** `r: &i32` и `rs: &S` **был одинаковым**, поэтому при вызове `f` тут `r = f(rs);`, lifetime ссылки `rs` **расширяется** до `r`, т.е. до последнего использования `r`, до вызова `println!("{}", *r);`. Что приводит к **ошибке компиляции**, т.к. **объект** `s`, на который ссылается `rs`, **деаллоцируется раньше**.<br>

<br>

## Заморозка
Существует 2 ситуации, когда объект деаллоцируется:
- **выход из скоупа**;
- **перезапись объекта** (**reassign**), т.е. когда присваиваем новый инстанс владельцу;

<br>

Пример 1: **dangling pointer** при **reassign**:
```rust
fn main() {
    let mut b = Box::new(1);
    let r = &*b;
    println!("{:?}", r);
    b = Box::new(1); // reassign: ❌ ERROR - cannot assign to `b` because it is borrowed
    println!("{:?}", r);
    println!("{:?}", b);
}
```

<br>

Rust следит за тем, была ли переменная инициализированна или нет, чтобы при reassign дропнуть старое значение.<br>
В примере выше, после reassign `b = Box::new(1);`, предыдущий объект (`Box::new(1)`) деаллоцируется (дропается), а значит ссылка `r` будет указывать на деаллоцированную память, т.е. станет **dangling pointer**. Поэтому borrow checker **запрещает** reassign **пока жива хотя бы одна ссылка** на предыдущее значение.<br>
Ссылка замораживает объект и все родительские объекты - reassign для них запрещен.<br>

<br>

Пример 2: **реаллокация Vec**:
```rust
fn main() {
    let mut v = vec![1,2,3];
    let item = &v[0];
    v.push(10);
    println!("{}", item); // ❌ ERROR - cannot borrow `v` as mutable because it is also borrowed as immutable
}
```

<br>

Код выше не скомпилится, т.к. метод `push` берет вектор по `mut` ссылку, а у нас уже есть **shared ссылка** на элемент из этого вектора.<br>
**Почему** `push` **берет вектор по** `mut` **ссылку**? Потенциально, при добавлении новых элементов в `Vec` может произойти **реаллокация**, а значит ссылку на первый элемент вектора `&v[0]`, которая лежит в `item`, **нельзя использвоать** после `push`, т.к. она **может указывать на деаллоцирвоанную память**.<br>

# Memory layout
Возможны 2 порядка полей в `struct` и  `enum`:
- **логический**, в котором структуру удобнее читать, это и есть порядок в объявлении `struct` и  `enum`;
- **физический**, в котором структура оптимальнее всего представлена в RAM;

<br>

В C/C++ пордяок полей в памяти такой же, как и в декларации типа, т.е. *логический* порядок **совпадает** с *физическим*.<br>
В Rust представление `struct` и  `enum` в памяти **не специфицированно**. Компилятор может **перемешать поля** `struct` и **варианты** `enum` так, **чтобы они занимали как можно меньше места в памяти**, т.е. *логический* порядок **может НЕ совпадать** с *физическим*.<br>

<br>

В Rust существует `#[repr]` атрибуты для спецификации порядка. В структурах может быть **padding** после последнего поля.<br>

# Return type polymorphism
```rust
trait Default {
    fn  default() -> Self; // `Self` - тип, для которого реализуется `Default`.
}

struct Cat;

impl Default for Cat {
    fn  default() -> Self {
        Self
    }
}

fn make_default<T: Default>() -> T {
    T::default()
}

fn main() {
    let cat: Cat = make_default();
}
```

<br>

Возможны два эквивалентных вызова `make_default`:
```rust
let cat: Cat = make_default();
let cat = make_default::<Cat>();
```

В первом случае, компилятор смотрит в левую часть и понимает, что **return type** - это `Cat`, т.к. сигнатура `T`, то компилятор понимает, что `T` это `Cat` и параметризует **make_default**: `make_default::<Cat>()`.<br>

<br>

# Monomorphization
**Мономорфизация** - замена компилятором вызова **generic function** на вызов конкретной функции.<br>
Компилятор может протайпчекать дженерик, но сгенерировать машинный код может только через мономорфизацию.<br>

При *мономорфизации* компилятор полагается на **вывод типов**. Пример:
```rust
fn make_default<T: Default>() -> (T,T) {
    (T::default(), T::default())
}

fn main() {
    let (cat1, cat2): (Cat, Cat) = make_default();
    let (cat1, cat2) = make_default::<Cat>();
}
```

В первом случае, компилятор смотрит в левую часть и понимает, что **return type** - это `(Cat, Cat)`, т.к. сигнатура `(T,T)`, то компилятор понимает, что `T` это `Cat` и параметризует **make_default**: `make_default::<Cat>()`.<br>

<br>

Компилятор не генерирует все возможные варианты для дженериков, наоборот, компилятор генерирует только нужные варианты функций во время мономорфизации.<br>

<br>

*Inline* допускают только **статические вызовы** и **мономорфизация**.<br>

# Fully qualified syntax
<br>

**Note**:
- **Для вызова метода трейта** - **трейт должен быть импортирован в пространство имен**.

<br>

**Терминология**:
- **methods** (**методы**) - это функции, которые **вызываются для конкретного экземпляра типа**, у таких функций **обязательно** должен быть `self` в качестве первого параметра;
- **associated functions** (**связанные функции**) - это функции, которые обычно **определены для типа в целом**, они не привязаны к инстансу типа, у них **нет** `self` параметра;
- **inherent methods/associated functions** (**собственные методы/связанные функции**) — это **методы/связанные функции**, определенные **напрямую для конкретного типа** (`struct` или `enum`) внутри `impl` блока, а **не** через реализацию трейта;

<br>

**Пример**:
```rust
struct S;

impl S {
  fn foo(&self) {println!("S")}
}

fn main() {
    let s = S;
    s.foo();
    S::foo(&s);
}
```

<br>

Два способа позвать метод:
- `s.foo();`
- `S::foo(&s);`

<br>

Возможна ситуация, когда в некотором трейте `X` имя метода совпадает с именем *inherent method*.<br>

**Пример**:
```rust
struct S1;
struct S2;

impl S1 {
  fn foo(&self) {println!("S1")}
}

trait X {
    fn foo(&self) {println!("X: foo default")}
    fn bar() {println!("X: bar default")}
}

trait Y {
    fn foo(&self) {println!("Y: foo default")}
    fn bar() {println!("Y: bar default")}
}

impl X for S1 {
    fn foo(&self) {println!("foo: S1 in X")}
    fn bar() {println!("bar: S1 in X")}
}

impl Y for S1 {
    fn bar() {println!("bar: S1 in Y")}
}

impl X for S2 {
    fn foo(&self) {println!("foo: S2 in X")}
    fn bar() {println!("bar: S2 in X")}
}

fn main() {
    let s1 = S1;
    s1.foo();
    S1::foo(&s1);

    X::foo(&s1);
    <S1 as X>::foo(&s1);

    // X::bar(); // ❌ - ERROR
    // s1.foo(); // ❌ - ERROR if no inherent method with name foo
    <S1 as X>::bar();
    <S1 as Y>::bar();
}
```

<br>

Как Rust разрешает **коллизии методов/связанных функций**:
- при коллизии *inherent* и *trait* - **побеждает** *inherent*;
- при коллизии в **2-х разных** *трейтах* - **ошибка компиляции**;

<br>

Чтобы **исключить коллизии** при вызове методов используется **Fully qualified syntax**.

Варианты вызова метода трейта `X`:
- `<S as X>::foo(&s1);`;
- `X::foo(&s1);`;
- `X::bar();`
- `s1.foo();`

<br>

*Первый вариант* **однозначный** - ошибки никода **не** будет.<br>
*Второй вариант* работает **только** для **методов**, т.к. методу всегда передается инстанс типа и **компилятор всегда знает тип**, для которого нужно искать реализацию `X`.<br>
*Третий вариант* не работает и приводит к ошибке, т.к. один и тот же трейт может может иметь дефолтную реализацию, а также множество реализаций для разных типов, поэтому для случая **связанных функций** - **не понятно какая именно реализация требуется**, т.к. инстанс не передается. Поэтому для варианта `X::bar();` **не понятно** какую имплементацию `bar` вызывать.<br>
*Четвертый вариант* может быть неоднозначным:
- если у типа есть *inherent метод* с таким названием - то он победит;
- но если *inherent метод* с таким названием **нет** и тип имплементит **несколько** трейтов, у которых могут **совпадать** имена методов, то даже не смотря на то, что инстанс известен, компилятор не понимает какой именно `foo()` звать. <br>

<br>

# Drop
```rust
pub const trait Drop {
    fn drop(&mut self);
}
```

Это называется **идиомой RAII**.<br>

<br>

Почему `drop` принимает `self` по **mut ссылке**? Если бы `drop` принимал `self` **по значению**, то **после выхода из скоупа** метода `drop`, этот `self` нужно было бы **дропнуть еще раз**.<br>

<br>

## Drop check
`Drop` влияет на анализ времени жизни.<br>

```rust
#[derive(Default)]
struct Wrapper<'a> {
    v: Option<&'a i32>,
}

impl<'a> Wrapper<'a> {
    fn push(&mut self, v: &'a i32) {
        self.v = Some(v);
    }
}

fn main() {
    let mut w = Wrapper::default();
    let v = 10;
    w.push(&v);
    // drop in reverse order:
    // 1) drop x
    // 2) drop w
}
```

<br>

Порядок `Drop` при **выходе из скоупа**:
- переменные **дропаются в порядке обратом объявлению**;
- поля в `struct`/`enum` **дропаются в порядке объявления**;

<br>

В примере выше первой дропается `x`, а потом `w`. Получается, после того, как значение в перменной `x` было деаллоцировано, значение типа `Wrapper` в переменной `w` еще живо и 
поле `v` структуры `Wrapper` продолжает ссылаться на деаллоцированную область памяти, т.е. фактически поле `v` структуры `Wrapper` это **dangling pointer**.<br>
Но код из примера выше компилируется, т.к. у `Wrapper` нет кастомной имплементации drop и компилятор точно знает, что во время деаллокации `Wrapper` этот **dangling pointer** использоваться не будет.<br>

<br>

**Но**, если добавить кастомную имплементацию `Drop` для типа `Wrapper`, то она уже может в теории использвоать этот **dangling pointer**. В таком случае код уже не скомпилируется и будет **compile time error**:
```rust
#[derive(Default)]
struct Wrapper<'a> {
    v: Option<&'a i32>,
}

impl<'a> Wrapper<'a> {
    fn push(&mut self, v: &'a i32) {
        self.v = Some(v);
    }
}

impl<'a> Drop for Wrapper<'a> {
    fn drop(&mut self) {
        println!("{:?}", self.v);
    }
}

fn main() {
    let mut w = Wrapper::default();
    let v = 10;
    w.push(&v); // ❌ - ERROR: borrowed value does not live long enough
    // `v` dropped here while still borrowed, borrow might be used here, when `w` is dropped and runs the `Drop` code for type `Wrapper`
}
```

# `swap`, `replace`, `forget`, `take`
- `pub const fn swap<T>(x: &mut T, y: &mut T)`
  - меняет 2 значения одного и того же типа по ссылке;
- `pub const fn replace<T>(dst: &mut T, src: T) -> T`
  - достает `T` из `dst`;
  - подставляем на место `dst` новое значение из `src`;
  - возвращет значение, которое раньше было в `dst`;
- `std::mem::forget<T>(t: T)`
  - **принимает владение** переданным значением `t` и намеренно **не вызывает его деструктор**, оставляя ресурсы (память, дескрипторы файлов) выделенными без очистки;
  - **типичный сценарий использования**: когда очисткой должен заниматься внешний по отношению к Rust код, т.е. происходит передача владения ресурсами через FFI;
- `pub fn take<T: Default>(dst: &mut T) -> T`
  - `T` должен имплементить `Default`;
  - похожа на `replace`, только вместо `src` используется `T::default()`;
  - возвращет значение, которое раньше было в `dst`, подкладывая вместо него `T::default()`;

<br>

Идея для `replace`:
```rust
fn replace(dst: &mut T, src: T) -> T {
    std::mem::swap(dst, &mut src);
    src
}
```

После `swap` в `src` будет лежать значение, которое **раньше было в** `dst`.<br>

<br>

Идея для `take`:
```rust
fn take(dst: &mut T) -> T {
    std::mem::replace(dst, T::default());
    src
}
```

# Deref/DerefMut
`Deref`/`DerefMut` управляют поведением операторов: `*` и `.`.<br>

```rust
pub trait Deref {
    type Target: ?Sized;
    fn deref(&self) -> &Self::Target;
}
```

Что делает `Deref`? `&P` неявно приводится к `&T` если `P` имплементит `Deref<Target=T>`.<br>

Пример:
```rust
const impl<T> Deref for Vec<T> {
    type Target = [T];

    fn deref(&self) -> &[T] {
        self.as_slice()
    }
}
```

<br>

На самом деле, `.len()` это метод `.len()` на слайсе, когда зовется `.len()` на ссылке на Vec, компилятор зовет `.len()` на слайсе.<br>

<br>

# `Index`/`IndexMut`
`Index`/`IndexMut` управляют поведением оператора обращения к элементу коллекции по индексу: `[]`.<br>

На самом деле `v[i]` рассахаривается в `v.index(i)`.<br>

<br>

# Итоговый пример - database shutdown
```rust
struct Database;

impl Database {
    fn shutdown(self) {}
}

struct App {
    db: Database,
}

impl Drop for App {
    fn drop(&mut self) {
        let db = self.db; // ❌ - ERROR: cannot move out of `self.db` which is behind a mutable reference
        db.shutdown();
    }
}
```

Метод `shutdown()` принимает объект `Database` по значению, но в метод `drop()` объект `App` передается по ссылке, поэтому вытащить из `App` объект `Database` не получится.<br>

Однако, можно сделать поле `db` **опциональным** и деструкторе использовать `take`:
```rust
struct Database;

impl Database {
    fn shutdown(self) {}
}

struct App{
    db: Option<Database>,
}

impl Drop for App {
    fn drop(&mut self) {
        let db = self.db.take().unwrap();
        db.shutdown();
    }
}
```

<br>

После этой строчки `let db = self.db.take().unwrap();` в `self.db` будет `None`, а в метод `shutdown()` будет передано значение типа `Database`.<br>

# Модули
Модули организовываются в **дерево модулей**. Порядок объявления модулей неважен, каждый модуль изолирован.<br>
**Crate** - это **единица компиляции**, это **root module** в *дереве модулей*.<br>

<br>

Содержимое модуля можно вынести в **отдельный файл**, в таком случае компиятор начинает работу с файла, соответствущего корневому модулю и рекурсивно парсит остальные модули:
- **main.rs**
```rust
mod foo;
```
- **foo.rs**
```rust
struct Foo;
```

<br>

**По умолчанию** `rustc` компилирует крейт типа `bin`, если нужна либа, то нужно в `rustc` это явно указать: для этого есть опция `--crate-type`:
- `--crate-type bin|lib|rlib|dylib|cdylib|staticlib|proc-macro`;

<br>

Опция `--extern foo=<path_to_object_foo_lib>` нужна чтобы передать **путь к объектному файлу крейта** `foo`, где `foo` - это некоторое имя в скоупе компилируемого `.rs` файла.<br>

<br>

**Пример**:
- **foo.rs**
```rust
pub fn hello() {
    println!("Hello!");
}
```
- **bar.rs**
```rust
fn main() {
    foo::hello();
}
```

<br>

- компилим **либу**
```bash
rustc foo.rs --crate-type rlib
```
- компилим **бинарь**
```bash
rustc bar.rs --extern foo=libfoo.rlib
```
- запускаем бинарь
```bash
./bar
Hello!
```

<br>

Имя `*.rs` файла для либы роли не играет, оно определяется флагом `--extern`.<br>
Например, можно в **bar.rs** изменить имя крейта `foo` на `xxx`:
- **bar.rs**
```rust
fn main() {
    xxx::hello();
}
```

После чего, опции `--extern` нужно передать **путь к объектному файлу крейта** `xxx`:
```bash
rustc bar.rs --extern xxx=libfoo.rlib
```

<br>

# Модификаторы видимости
По умолчанию, **все имена приватные** и **видны только внутри текущего модуля** и **его детей**:
```rust
mod a {
    struct Foo;
    mod b {
        use super::Foo;
    }
}
mod x {
    use super::a::Foo; // ❌ - ERROR
}
```

<br>

**Модификаторы**:
- `pub(super)` - делает имя **доступным** в родительском модуле;
- `pub(crate)` - делает имя доступным **в данном крейте** из любого места, но имя все еще **не** доступно из **других** крейтов;
- `pub(in some::path)` - делает имя **доступным** в **модуле** `some::path` и **всех** его **подмодулях**;
  - `some::path` должен быть путем к любому **предку** данного модуля; 
  - **по умолчанию**, в качестве пути `some::path` используется **текущий модуль**, поэтому *декларация item* видна в **текущем модуле** и **всех** его **подмодулях**;
- `pub` - делает имя **доступным в других крейтах**, другими словами, крейты, зависимые от данного крейта будут видеть **все items** объявленные как `pub`;
  - 

<br>

Note:
- все что помечено как `pub` - это **public API крейта**;
- `pub` не работает для **методов** `trait` и для **вариантов** `enum`, считается, что видимость **методов** `trait` такая же как у **всего** `trait`, аналогично и для `enum`;

<br>

**Пример**
```rust
fn main() {
    // use crate::r::R; // ❌ - ERROR
    use crate::r::a::e::E2; // ✅ - Ok
}

mod r {
    struct R;
        // use crate::r::a::e::E1; // ❌ - ERROR
        use crate::r::a::e::E2; // ✅ - Ok
        // use crate::r::a::e::E3; // ❌ - ERROR
        // use crate::r::a::e::E4; // ❌ - ERROR
        use crate::r::a::e::E5; // ✅ - Ok
    // use a::A; // ❌ - ERROR
    pub mod a {
        // use crate::r::a::e::E1; // ❌ - ERROR
        use crate::r::a::e::E2; // ✅ - Ok
        use super::R;           // ✅ - Ok
        use crate::r::a::e::E3; // ✅ - Ok
        use crate::r::a::e::E4; // ✅ - Ok
        use crate::r::a::e::E5; // ✅ - Ok
        struct A;
        pub mod b {
            struct B;
            use crate::r::a::e::E4; // ✅ - Ok
            pub mod c {
                struct C;
            }
            pub mod d {
                struct D;
                use super::super::e::E3; // ✅ - Ok
                // use crate::r::a::e::E3; // ✅ - Ok
            }
        }
        // use crate::r::a::e::g::G2; // ❌ - ERROR
        pub mod e {
            struct E1;
            pub(crate) struct E2;
            pub(super) struct E3;
            pub (in crate::r::a) struct E4;
            pub (in crate::r) struct E5;
            pub mod f {
                struct F;
                use super::E1; // ✅ - Ok
                use crate::r::a::e::g::G2; // ✅ - Ok
            }
            use crate::r::a::e::g::G2; // ✅ - Ok
            pub mod g {
                struct G1;
                pub(super) struct G2;
            }
        }
    }

    mod w {
        struct W;
        pub mod x {
            struct X;
            pub mod z {
                struct Z;
                // use crate::r::a::e::E3; // ❌ - ERROR
                // use super::super::super::a::e::E3; // ❌ - ERROR
            }
            pub mod y {
                struct Y;
            }
        }
        pub mod s {
            struct S;
            pub mod t {
                struct T;
                use crate::r::a::e::E5; // ✅ - Ok
            }
            pub mod u {
                struct U;
                use crate::r::a::e::E2; // ✅ - Ok
                // use super::super::super::a::e::E2; // ✅ - Ok
            }
        }
    }
}
```

# Реэкспорт
**Реализацию** удобно организовывать **иерархически**, но для **использования** удобно **плоское api**.<br>
К `use` тоже применимы **модификаторы видимости**, что позволяет делать **реэкспорт**.<br>
А уже через *реэкспорт* можно сделать *api крейта* **плоским**:
```rust
mod x {
    pub use y::foo::Foo;
    mod y {
        pub mod foo {
            pub struct Foo;
        }
    }
}

mod api {
    pub use crate::x::Foo;
}

fn main() {
    let foo = api::Foo;
}
```

# Cargo
С точки зрения *Rust*: **crate** - это **единица компиляции**.<br>
С точки зрения *cargo*: **crate** - это **пакет** (**package**).<br>

- **Cargo.toml**
```toml
[package]
name = "foo"
version = "0.1.0"
edition = "2024"

[dependencies]
rand = "0.10.2"

[lib]
# name = "lib"
name = "w"
```
- **lib.rs**
```rust
pub mod foo;
pub fn add(x:u64, y:u64) -> u64 {
    x + y
}
```
- **foo.rs**
```rust
pub fn add2(x:u64, y:u64) -> u64 {
    x + y
}
```
- **main.rs**
```rust
mod foo;

fn main() {
    let x = w::add(1, 5);
    let x = w::foo::add2(1, 5);
    let x = foo::add2(1, 5);
}
```

<br>

В **Cargo.toml** для либы было выбрано имя `w`, это имя **глобально доступно** в любом месте **binary** крейта. Это значит, что не нужно делать `mod w;` или `use w;`. Имя либы уже в скоупе **binary** крейта.
Чтобы обратиться к items из либы, нужно использовать пути, начинающиеся с имени либы: `w::...`.<br>
Имя либы можно поменять на `lib`, тогда к либе можно обращаться через `lib::`.<br>
Если в **Cargo.toml** имя либы не указано явно, то в качестве имени либы используется имя пэкеджа, в примере выше это `foo`.
